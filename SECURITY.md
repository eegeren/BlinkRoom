# BlinkRoom security model

## End-to-end encryption

BlinkRoom version 1 encrypts shared text, links, filenames, MIME types, file sizes, and file bytes in participating browsers with AES-256-GCM. A random 256-bit room key is generated by the creator’s browser and placed after `#` in the invite URL. URL fragments are not included in HTTP requests, and the application does not put this key in API bodies, query parameters, cookies, local storage, or the database.

Text and link items use a fresh 96-bit IV and authenticated additional data binding the ciphertext to the room slug, item ID, purpose, and crypto version. Files use 4 MiB chunks. Each chunk has a fresh 96-bit IV and AAD containing the room slug, item ID, zero-based chunk index, and version. The binary format is:

```text
BRF1 | chunkSize:u32 | chunkCount:u32 |
  repeated(chunkIv:12 bytes | ciphertextLength:u32 | AES-GCM ciphertext)
```

Encrypted filename, MIME type, original size, and temporary sender label are stored in a separate AES-GCM metadata envelope. Storage objects use random item UUIDs and contain ciphertext only. Downloads are decrypted by the browser.

## What the server can see

The server necessarily sees room slugs, room status and expiration, opaque participant IDs, online presence, item IDs, coarse item type (`TEXT`, `LINK`, `IMAGE`, or `FILE`), ciphertext sizes, timestamps, storage keys, IP/network metadata available to infrastructure, and encrypted payloads. It does not receive the room encryption key, message text, link URL, original filename, original MIME type, or plaintext file bytes.

For direct transfers, Socket.IO relays validated SDP offers/answers and ICE candidates only between temporary participants already joined to the same active room. Signaling is size- and rate-limited and never includes content, filenames, or the room encryption key. File bytes travel through the WebRTC DataChannel as BlinkRoom AES-GCM ciphertext; WebRTC's DTLS layer supplements rather than replaces application-level E2EE. Failed or unavailable direct transfers use the same encrypted blob through temporary storage.

When R2 is selected, the browser uploads only the already-encrypted binary through short-lived presigned multipart URLs. The server chooses opaque object keys and R2 receives `application/octet-stream` without original filename/MIME metadata. R2 credentials stay server-side. Download URLs are issued only while the database says the room is active and expire after a short configurable TTL. A URL issued immediately before destroy/expiration may remain technically usable until its TTL ends; it retrieves only AES-GCM ciphertext, but short TTLs and private buckets reduce that residual exposure.

Owner authorization uses a separate random token. Only its SHA-256 hash is stored in PostgreSQL. The owner token is not a content-encryption key.

## Protection offered

E2EE protects stored room content against:

- a database disclosure;
- an object-storage disclosure;
- server operators reading stored shared content.

AES-GCM authentication also rejects modified ciphertext, incorrect keys, and reordered file chunks.

## Out of scope

E2EE does not automatically protect against:

- a compromised device, browser, or malicious browser extension;
- someone who receives or steals the complete invite link;
- screenshots, copied text, or downloaded copies;
- malicious JavaScript served by a compromised BlinkRoom deployment;
- traffic metadata, IP logs, CDN logs, reverse-proxy logs, or abuse-protection records.

BlinkRoom therefore does not claim “zero logs,” anonymity, or immunity from compromise.

WebRTC is not an anonymity system. During direct connection establishment, participants may learn network-address information about one another depending on browser, ICE candidates, and whether TURN relay is used. BlinkRoom infrastructure can also observe signaling timing and connection metadata. A TURN service can improve connectivity and reduce direct address exposure, but it still observes transport metadata and never receives BlinkRoom plaintext or the room key.

## Key lifecycle

The key is reconstructed from the URL fragment after refresh and held as a non-extractable `CryptoKey` in browser memory. Missing fragments show a missing-key state. Invalid keys and authentication failures show a generic unlock error. When a room expires or is destroyed, decrypted item state is dropped, Blob URLs are revoked, pending uploads are aborted, and the `CryptoKey` reference is released. JavaScript garbage collection does not provide a guaranteed secure memory wipe.

## Versioning

All envelopes and file AAD use crypto version `1`. Unsupported versions fail closed. A future format change must introduce a new version and retain explicit migration/compatibility rules.
